01

Django

Qué es, en qué cree y cómo piensa.

⏱ 15 s · Sección de conceptos: entender Django antes de instalar nada.
Punto de partida

¿Qué es Django?

Framework web completo

Gratuito y open source, escrito en Python. Nació en 2005 en el Lawrence Journal-World.

Lado del servidor

Trabaja el backend: enrutado, base de datos, autenticación, formularios, plantillas.

Sin ataduras

Soporta múltiples bases de datos y se despliega en varios servidores web.

✓
Detrás de sitios como Instagram, Mozilla, Pinterest o Eventbrite: Django escala.
⏱ 2 min · Django es un framework "baterías incluidas": no empiezas con una página en blanco. Es gratis, open source y con una comunidad enorme. Nació en una redacción de periódico, de ahí su foco en contenido y fechas.
Cómo piensa

Filosofía de Django

Agilidad

Del concepto al producto sin montar media infraestructura.

Bajo acoplamiento

Componentes independientes que puedes cambiar por separado.

DRY

Don't Repeat Yourself: la lógica vive en un solo lugar.

URLs limpias

Direcciones legibles y mapeadas explícitamente.

Versatilidad

De un blog a una plataforma enorme con la misma base.

MTV

Model Template View: una variación del clásico MVC.

⏱ 2 min · Estos principios explican muchas decisiones del framework. DRY es el que más notarás: un modelo, un serializer, una vista. MTV es la pieza que viene en la siguiente slide.
El patrón

MTV: tres preguntas, tres piezas

¿Cómo se almacena el dato?
Modelo

La clase Python que describe la tabla en la base de datos.

¿Qué dato se muestra?
Vista

La función o clase que decide qué consultar y qué responder.

¿Cómo se muestra el dato?
Template

El HTML con marcadores que da forma a la respuesta.

⏱ 2 min · Estas tres preguntas son el esqueleto de toda app Django. Los noruegos dirían: modelo = datos, vista = lógica, template = presentación. El registro de URLs conecta las peticiones con las vistas.
La idea en una imagen

El flujo de Django

⏱ 2.5 min · Recorrer el diagrama: el navegador pide una URL, urls.py resuelve qué vista la atiende, la vista consulta los modelos (que hablan SQL con la base de datos) y renderiza un template. El resultado vuelve como HTML. Este es el corazón de Django.

Preparación

Del entorno virtual al primer servidor corriendo.

⏱ 15 s · Manos a la obra: creamos el proyecto taller y la app blog.
Paso 1

El entorno virtual

Un entorno aislado con su propia copia de Python y sus dependencias.

zsh — terminal
$ mkdir taller && cd taller $ python3 -m venv .venv $ source .venv/bin/activate # Windows: .venv\Scripts\activate (.venv) $
i
Antes se usaba virtualenv; hoy venv viene incluido en Python. El prompt (.venv) confirma que está activo.
⏱ 2 min · El entorno virtual evita ensuciar el Python del sistema y que dos proyectos choquen de versiones. Todo lo que instalemos vive en .venv, dentro del proyecto.
Paso 2

Instalar Django

zsh — terminal

✓
pip freeze deja las versiones exactas en requirements.txt: tu proyecto es reproducible en otra máquina.
⏱ 1.5 min · pip es el gestor de paquetes de Python. Fijamos la serie 5.2 (LTS, soporte extendido) y congelamos versiones. En el taller de 2017 esto era "pip install django" sin más.

Crear el proyecto

✓

⏱ 1.5 min · Un proyecto Django se crea con startproject. El nombre taller es nuestro caso de ejemplo. El punto final es el detalle moderno que no estaba en los talleres originales.

03

Las piezas

Modelos, ORM, admin, vistas y plantillas con un blog mínimo.

⏱ 15 s · Ahora conectamos todo: cada archivo que Django generó y qué va dentro.
Organización

Proyecto y aplicación

Proyecto

Contiene la configuración y los componentes del sitio: settings, urls, wsgi/asgi. Nuestro taller.

Aplicación

Un componente con una funcionalidad concreta: blog, usuarios, foros, galería… Cada una con sus modelos y vistas.

i
Un proyecto puede contener muchas apps; una app puede reutilizarse en varios proyectos (Django trae varias de serie: admin, auth…).
⏱ 1.5 min · Esta distinción confunde al principio: el proyecto es el pegamento y la configuración; las apps son las funcionalidades. Nuestro caso: proyecto taller + app blog.
Configuración

settings.py

taller/settings.py
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "blog",
]

LANGUAGE_CODE = "es-pe"
TIME_ZONE = "America/Lima"
i
Aquí viven la base de datos, los idiomas, la zona horaria y las apps activas. En producción suele haber uno por entorno (local, testing, prod).
⏱ 2 min · INSTALLED_APPS es la lista de apps activas: las de Django más la nuestra. Con LANGUAGE_CODE y TIME_ZONE adaptamos el proyecto a Perú. Si olvidas registrar blog aquí, sus modelos no existen para Django.
Enrutado

urls.py

taller/urls.py
from django.contrib import admin
from django.urls import path

from blog import views

urlpatterns = [
    path("admin/", admin.site.urls),
    path("articulos/", views.lista_articulos, name="lista_articulos"),
]
i
Django 2+ usa path() con convertidores (<int:pk>); en 2017 esto se escribía con url() y expresiones regulares. Un urls.py por app mantiene todo ordenado.
⏱ 2 min · urls.py mapea direcciones a vistas. La primera ruta es el admin que Django trae; la segunda es la nuestra. name= permite referenciar la URL desde plantillas sin repetir la ruta.
Pieza 1

Los modelos

  • Descripciónlos datos en código Python que se reflejan en tablas de la base de datos.
  • SQL por detráscada consulta ejecuta SQL y devuelve objetos Python cómodos.
  • models.pycada aplicación declara ahí sus modelos.
✓
Nuestro blog: un modelo Articulo con título, cuerpo, estado de publicación y fecha de creación.
⏱ 1.5 min · Un modelo es una clase = una tabla; cada atributo = una columna. Las migraciones traducen los cambios a la base de datos. Nunca escribimos CREATE TABLE a mano.
Pieza 1

models.py

blog/models.py
from django.db import models


class Articulo(models.Model):
    titulo = models.CharField(max_length=120)
    cuerpo = models.TextField()
    publicado = models.BooleanField(default=True)
    creado = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.titulo

    class Meta:
        ordering = ("-creado",)
i
CharField y TextField son los campos de texto; auto_now_add pone la fecha al crear. __str__ hace legible el objeto en el admin.
⏱ 2.5 min · Recorrer cada campo. publicado con default=True; creado se rellena solo. Meta.ordering ordena por fecha descendente: el blog muestra lo más nuevo primero. Tras editarlo toca migrar.
Pieza 1

Las migraciones

El historial versionado de los cambios de tus modelos, en archivos Python.

1

Cambias models.py

añades o modificas un campo
→
2

makemigrations

genera el archivo de migración en migrations/
→
3

migrate

aplica los cambios a la base de datos
!
Cambiaste un modelo y no migraste: la tabla no existe. Es el error más frecuente al empezar.
⏱ 2 min · makemigrations crea código Python legible (puedes revisarlo e incluso versionarlo); migrate lo aplica. Las migraciones van al repositorio: son parte del proyecto.
Pieza 2

El ORM de Django

Object Relational Mapping: mapeo objeto-relacional.

  • Sin SQLconsultas y escrituras con métodos Python; el ORM genera el SQL.
  • Objetoscrear, modificar, eliminar y consultar de forma individual o en conjunto.
  • Portableel mismo código funciona en PostgreSQL, MariaDB, SQLite…
✓
La puerta de entrada es python manage.py shell: un intérprete con Django cargado.
⏱ 2 min · El ORM es el interfaz entre tus objetos Python y la base de datos. Es potente y expresivo, y genera SQL eficiente en la mayoría de los casos. Cuando necesites, puedes caer a SQL con query.raw().
Pieza 2

ORM en acción

python manage.py shell
>>> from blog.models import Articulo >>> Articulo.objects.create(titulo="Hola Django", cuerpo="Mi primer post") <Articulo: Hola Django> >>> Articulo.objects.all() <QuerySet [<Articulo: Hola Django>]> >>> Articulo.objects.filter(publicado=True).order_by("-creado") <QuerySet [<Articulo: Hola Django>]>
i
create() inserta, all() trae todo, filter() filtra y order_by() ordena. Detrás de cada línea hay SQL generado por Django.
⏱ 2 min · Esta es la forma más rápida de tocar datos sin pasar por el admin. Los QuerySet son perezosos: la consulta se ejecuta cuando iteras o imprimes el resultado.

Pieza 4

Las vistas

  • Entradareciben un objeto con la petición: método (GET/POST), ruta, datos…
  • Salidadevuelven una respuesta: HTML renderizado, una redirección o un error.
  • views.pycada aplicación declara ahí sus vistas; pueden ser funciones o clases.
✓
Nuestra primera vista: consultar los artículos publicados y pasarlos a una plantilla.
⏱ 1.5 min · La vista es el cerebro: decide qué datos usar y qué plantilla renderizar. Empezamos con funciones (más simples de leer); las vistas basadas en clases llegan cuando el CRUD se repite.
Pieza 4

views.py

blog/views.py
from django.shortcuts import render

from blog.models import Articulo


def lista_articulos(request):
    articulos = Articulo.objects.filter(publicado=True)
    return render(request, "blog/lista.html", {"articulos": articulos})
i
render() une tres cosas: la petición, la plantilla y el contexto (los datos que la plantilla usará).
⏱ 2 min · Tres líneas de negocio: consulta, contexto, render. El request casi nunca se usa aquí, pero es la puerta a todo (usuario, método, parámetros). Esa vista ya está enlazada en urls.py.
Pieza 5

Las plantillas

  • HTML + etiquetas{{ variable }} inserta datos; {% etiqueta %} controla la lógica.
  • ¿Dónde viven?en templates/ de cada app, o una carpeta global del proyecto.
  • Herencialas plantillas se extienden y se reutilizan: una base, muchas páginas.
✓
El HTML final se arma con datos en el servidor; el navegador solo recibe el resultado.
⏱ 1.5 min · Las plantillas no son Python: son HTML con un mini-lenguaje. La herencia es su superpoder: defines la estructura una vez (base.html) y cada página rellena sus bloques.
Pieza 5

Herencia de plantillas

blog/templates/base.html
<!doctype html>
<html lang="es">
<head>
  <title>
    {% block titulo %}Mi blog{% endblock %}
  </title>
</head>
<body>
  {% block contenido %}{% endblock %}
</body>
</html>
blog/templates/blog/lista.html
{% extends "base.html" %}

{% block titulo %}Artículos{% endblock %}

{% block contenido %}
  {% for articulo in articulos %}
    <h2>{{ articulo.titulo }}</h2>
  {% endfor %}
{% endblock %}
i
extends hereda la base; block rellena las partes; for recorre el contexto que envió la vista.
⏱ 2.5 min · La plantilla lista.html solo define lo que cambia; base.html se escribe una vez. {{ articulo.titulo }} escapa el HTML por defecto: protección XSS incluida.
Pieza 6

Archivos estáticos

CSS, JavaScript e imágenes: lo que no cambia con cada petición.

  • static/una carpeta por app, o una global del proyecto.
  • {% static %}genera la URL correcta de cada archivo en las plantillas.
  • collectstaticreúne todo para servirlo en producción (nginx, S3…).
taller/settings.py
STATIC_URL = "static/"
STATICFILES_DIRS = [BASE_DIR / "static"]
⏱ 1.5 min · En desarrollo Django sirve los estáticos él mismo; en producción los recoge collectstatic y los sirve nginx o un CDN. Nunca los pongas a mano en el HTML: usa {% static %}.

El puente

Django REST Framework

Django pone la base

Modelos, ORM, autenticación, admin y migraciones: el motor de datos y la lógica.

DRF añade la capa API

Serializers, vistas y routers para exponer todo eso como una API REST con JSON.

i
Cuando tu web necesite una app móvil, una integración o un frontend separado, el siguiente paso natural es DRF.
⏱ 1.5 min · Mención breve, sin entrar en detalle: DRF es la evolución natural de lo que aprendiste hoy. Los mismos modelos y lógica se expone como API. Hay una charla completa dedicada a DRF si te interesa el tema.
Aprendiendo de los errores

Errores comunes

Olvidar la app en INSTALLED_APPS

Síntoma: no aparecen tablas, ni admin, ni plantillas. Django no sabe que tu app existe.

Cambiar el modelo sin migrar

makemigrations + migrate después de cada cambio. Sin eso, la tabla no existe.

DEBUG=True en producción

Expone información interna. Se apaga con variables de entorno, igual que SECRET_KEY.

Commitear la base de datos

db.sqlite3 y .venv/ van al .gitignore: son locales, no código.

⏱ 2 min · Estos cuatro errores son los que más se repiten al empezar. El primero es el clásico "no funciona nada y estaba bien el código": faltaba registrar la app. Los otros tres son de higiene de proyecto.
