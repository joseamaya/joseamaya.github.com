Introducción

Chatbots y la importancia de la memoria

Los chatbots deben dar respuestas coherentes y útiles. Sin memoria, un chatbot “olvida” lo que el usuario le dijo antes y lo obliga a repetir datos en cada mensaje.

1

Respuestas coherentes

Recordar el contexto y los detalles permite respuestas más relevantes.

2

La memoria es una función cognitiva

Ayuda al bot a adaptarse y a ofrecer respuestas más útiles.

3

Corto + largo plazo

Incorporaremos ambas en un chatbot de Telegram con LangChain, LangGraph y MongoDB.

Enfatiza la analogía humana: la memoria es una función cognitiva. Un bot sin memoria es como atender a alguien con amnesia en cada mensaje. Resolveremos esto en dos escalas: corto plazo (el hilo) y largo plazo (los hechos).

¿Por qué Telegram?

Telegram es una app de mensajería que permite crear bots conversacionales fácilmente.

Usamos un webhook en FastAPI que recibe las actualizaciones de Telegram en tiempo real.

Usuario → Telegram → Webhook (POST /webhook/{token}) │ ▼ Bot (procesa) │ ▼ Respuesta al usuario por Telegram
Explica por qué webhook y no polling: menor latencia y menos consumo. Menciona que FastAPI encaja bien por ser async, que es justo lo que necesitamos para LangGraph asíncrono.

¿Qué es un Prompt?

Un prompt es el texto que le das al modelo para guiar su respuesta. Piensa en él como la personalidad + instrucciones del bot.

Estás a punto de jugar a un juego de prueba de Turing como parte de un experimento.
Te emparejarán con un humano en una conversación de chat.
Tu tarea es interpretar al siguiente personaje, convenciendo al humano de que eres un humano real.

## Personalidad de Lucía

{memory_context}

Proporciona respuestas de texto simple, sin indicadores de formato ni metacomentarios.
"""

Aquí aparece la primera pieza clave: el prompt tiene un hueco, memory_context, que se rellena con la memoria de largo plazo. Es el puente entre la base de datos y el modelo.

MEMORY_ANALYSIS_PROMPT = """Extraiga y formatee datos personales importantes del usuario a partir de su mensaje.

¿Qué es una cadena (chain)?

Las chains son secuencias de operaciones que procesan y transforman entradas para producir salidas. Son como tuberías que conectan componentes.

Memory chain
Extrae lo importante

Analiza cada mensaje y decide qué vale la pena recordar.

Character chain
Responde en personaje

Genera la respuesta final usando el contexto de memoria.

Analogía de la tubería: cada etapa transforma la información. En nuestro proyecto solo hay dos chains, lo que mantiene el diseño simple y fácil de depurar.
LangChain

Chains en código

Memory chain · extracción estructurada
def get_memory_chain():
    model = ChatOpenAI(model="gpt-4o", temperature=0).with_structured_output(MemoryAnalysis)
    prompt = ChatPromptTemplate.from_template(MEMORY_ANALYSIS_PROMPT)
    return prompt | model
Character chain · responde en personaje
def get_character_chain():
    model = ChatOpenAI(model="gpt-4o", temperature=0.5)
    system_message = CHARACTER_PROMPT
    prompt = ChatPromptTemplate.from_messages(
        [
            ("system", system_message),
            MessagesPlaceholder(variable_name="messages"),
        ]
    )
    return prompt | model
Hoy cambiaríamos gpt-4o por el modelo que prefieras: LangChain es agnóstico del proveedor.
Revela primero la memory chain y luego la character chain. Señala el operador | (pipe) de LangChain Expression Language: encadena prompt y modelo. temperature=0 para extracción determinista; 0.5 para respuestas con algo de creatividad.

def create_workflow_graph():
    g = StateGraph(StateBot, context_schema=Context)
    g.add_node("memory_extraction_node", memory_extraction_node)
    g.add_node("memory_injection_node", memory_injection_node)
    g.add_node("generate_response", generate_response)
2 · Aristas y retorno
    g.add_edge(START, "memory_extraction_node")
    g.add_edge("memory_extraction_node", "memory_injection_node")
    g.add_edge("memory_injection_node", "generate_response")
    g.add_edge("generate_response", END)
    return g
Lee el grafo en voz alta: START → extracción → inyección → generación → END. Es lineal a propósito: primero aprende, luego recuerda, luego responde. El context_schema inyecta el user_id en los nodos; la compilación con checkpointer y store se hace una vez al arrancar (slide siguiente).
Estado

El estado de la conversación

El estado hereda de MessagesState de LangGraph y almacena:

  • El historial de mensajes (heredado).
  • El contexto de memoria personalizado (memory_context).

El Context (schema) inyecta el user_id en cada nodo para separar la memoria por usuario.

from dataclasses import dataclass
from langgraph.graph import MessagesState


@dataclass
class Context:
    user_id: str


class StateBot(MessagesState):
    memory_context: str
El estado es la pizarra compartida del grafo. MessagesState ya trae la lista de mensajes; nosotros le añadimos memory_context. El Context es distinto del State: no se persiste en el hilo, se pasa en cada invocación y sirve para resolver el namespace de largo plazo.
Nodos

Los tres nodos del grafo

1 · Memory extraction
Aprende

Analiza el último mensaje. Si es importante, lo guarda en el store (que vectoriza solo).

2 · Memory injection
Recuerda

Toma el último mensaje, busca por similitud semántica y construye el contexto de memoria.

3 · Generate response
Responde

Usa el character chain, incorpora la memoria y mantiene la consistencia.

Aprender → recordar → responder. Simple y ordenado.

Este es el corazón de la charla. Cada nodo tiene una única responsabilidad, lo que hace el sistema fácil de testear y de extender.

Short term

Memoria a corto plazo

Es el contexto y los mensajes recientes de una sola conversación.

LangGraph la trata como parte del estado interno del agente, persistido con un checkpointer por cada hilo de conversación.

En desarrollo: InMemorySaver (antes MemorySaver). En producción: MongoDBSaver de langgraph.checkpoint.mongodb.
El checkpointer guarda el estado completo del grafo. La clave es el thread_id: cada chat_id de Telegram es un hilo distinto. Nota técnica: InMemorySaver es solo para desarrollo; en producción usamos MongoDBSaver (el mismo saver expone métodos async, ya no hay un AsyncMongoDBSaver aparte).
Short term

La ventana de contexto no es infinita

Con memoria de corto plazo activada, las conversaciones largas superan la ventana del LLM. La doc oficial recomienda gestionarla:

Recortar
trim_messages

Conservar solo los últimos N tokens antes de llamar al modelo.

Resumir
SummarizationNode

Resumir los mensajes antiguos y reemplazarlos por el resumen.

Borrar
RemoveMessage

Eliminar mensajes del estado de forma permanente.

Y del lado de la persistencia: prune(...) y TTL en el checkpointer evitan que los checkpoints crezcan sin control.
Punto que se suele omitir: la memoria de corto plazo se llena. Menciona trim_messages, summarization y RemoveMessage, y que el checkpointer de MongoDB soporta ttl y prune para no acumular checkpoints. Enlaza con la slide de gotchas.
Long term

Memoria a largo plazo

Son conocimientos que se comparten entre conversaciones distintas: datos permanentes como el perfil del usuario o hechos guardados.

LangGraph provee la API de Store (put, get, search), organizada por namespace. Con index_config, el search es semántico.

from langgraph.store.mongodb import MongoDBStore, create_vector_index_config

store = MongoDBStore.from_conn_string(
    settings.MONGO_DB_URL, collection_name="memories",
    index_config=create_vector_index_config(embed=embeddings, dims=1536),
)
ns = (user_id, "memories")
store.put(ns, memory_id, {"data": "Le encanta Star Wars"})
store.search(ns, query="¿qué le gusta?", limit=5)
La diferencia práctica: aunque borres las tablas de corto plazo, el bot sigue sabiendo tu nombre. Eso lo demostraremos en la slide de resultados. Explica que el namespace normalmente es (user_id, "memories") para aislar por usuario.
Long term

Búsqueda semántica

Buscar por significado, no por palabras exactas. En vez de comparar texto literal, convertimos frases en vectores (embeddings) y encontramos los que se parecen en sentido.

Búsqueda normal
❌ “auto” ≠ “carro”

Coincidencia literal de palabras.

Búsqueda semántica
✅ “auto” ≈ “carro”

Coincidencia por significado.

Por eso el usuario puede decir “mi nombre” o “cómo me llamo” y aun así lo encontramos.

Esta es la razón técnica por la que usamos un vector store y no un LIKE de SQL. Los embeddings convierten el significado en geometría: cerca = parecido.
Memoria

¿Cómo modela LangGraph la memoria?

Memoria corta: checkpointer que guarda el estado al ejecutar el grafo.

Memoria larga: Store de larga duración que el agente consulta cuando hace falta.

Implementaciones: InMemorySaver/MongoDBSaver para el hilo y MongoDBStore para los hechos.
Resume el modelo mental: checkpointer para el hilo, store para los hechos. LangGraph te da los ganchos; nosotros decidimos qué guardar y cuándo buscarlo. Menciona MongoDBStore como la implementación oficial para producción.

Compilar el grafo una sola vez

El checkpointer y el store se crean al arrancar la app. El grafo se compila una vez con ambos y se reutiliza en cada mensaje.

1 · Setup (una vez, en el lifespan)
from langgraph.checkpoint.mongodb import MongoDBSaver

with MongoDBSaver.from_conn_string(
    settings.MONGO_DB_URL, db_name=settings.MONGO_DB_NAME,
) as checkpointer:
    graph = create_workflow_graph().compile(
        checkpointer=checkpointer,
        store=store,
    )
2 · Por mensaje
async def reply(self, chat_id, user_id, text):
    config = {"configurable": {"thread_id": str(chat_id)}}
    await self.graph.ainvoke(
        {"messages": [HumanMessage(content=text)]},
        config,
        context=Context(user_id=str(user_id)),
    )
    state = await self.graph.aget_state(config)
    return state.values["messages"][-1].content
Revela en dos pasos. Clave de rendimiento: no crear el checkpointer ni recompilar el grafo por mensaje (eso abriría un MongoClient nuevo cada vez). thread_id aísla el hilo; user_id alimenta el namespace de largo plazo. ainvoke ejecuta el grafo y aget_state recupera el estado final.

¿Qué se guarda?

Al usar checkpointer=, LangGraph genera y administra sus propias colecciones. No escribimos el esquema a mano.

ColecciónQué guarda
checkpointsSnapshot del estado por hilo (mensajes y canales)
checkpoint_writesEscrituras pendientes de cada nodo
El hilo de la conversación y el estado del grafo se guardan automáticamente. Nosotros solo definimos el estado.
Muestra que no escribimos el esquema a mano: el checkpointer crea y administra sus colecciones. Nos concentramos en el negocio. Si preguntan, los checkpoints crecen con el tiempo y conviene una política de retención (lo veremos en gotchas).
MongoDB

Atlas Vector Search

Es el motor de búsqueda vectorial de MongoDB Atlas: indexa embeddings y hace KNN por similitud con el stage $vectorSearch. No confundir con Atlas Search, que es búsqueda de texto (BM25).

Vectorial
🧠 $vectorSearch

KNN aproximado (HNSW) sobre el campo de embeddings.

Filtros
⚙️ Campos del índice

Filtra por metadatos declarados, como user_id.

Híbrida
🔠 Texto + vector

Combina BM25 y similitud con Reciprocal Rank Fusion.

Aclara la confusión más común: Atlas Search (texto/facetas) y Atlas Vector Search ($vectorSearch) son motores distintos. El índice de embeddings que usamos es de Vector Search, y los filtros por campo hay que declararlos en ese índice.

MongoDBStore

Long term · calidad

Mejorar el recall: híbrida + reranking

La similitud vectorial sola no siempre basta. Atlas y LangChain ofrecen dos mejoras.

Búsqueda híbrida
BM25 + vector

Combina coincidencia de texto y semántica con Reciprocal Rank Fusion.

Reranking
Voyage AI

Un reranker reordena los candidatos por relevancia real.

store = MongoDBStore(
    collection,
    index_config=create_vector_index_config(embed=embeddings, dims=1536),
    rerank_config=RerankConfig(model="rerank-2.5-lite", top_k=3),
)

El reranking nativo requiere Atlas 8.3+ y Native Reranking habilitado.

Mejoras opcionales de recuperación. La híbrida (texto + vector con RRF) ayuda cuando el usuario usa términos exactos; el reranking reordena el top-k con un modelo de Voyage. Menciona que MongoDBStore lo soporta vía rerank_config, pero requiere Atlas 8.3+.

Inyección

Nodo de inyección de memoria

Buscamos por similitud semántica con asearch; el namespace por usuario garantiza que cada quien recupere solo sus recuerdos.

1 · Namespace y último mensaje
async def memory_injection_node(state, runtime: Runtime[Context]):
    ns = (runtime.context.user_id, "memories")
    last_message = state["messages"][-1].content
2 · Buscar y construir el contexto
    try:
        items = await runtime.store.asearch(
            ns, query=last_message, limit=5,
        )
        memory_context = "\n".join(i.value["data"] for i in items)
        return {"memory_context": memory_context}
    except Exception as e:
        print(f"Error recuperando memorias: {e}")
        return {"memory_context": ""}
El namespace (user_id, "memories") es crítico: garantiza que cada usuario recupere solo sus recuerdos. Este nodo sí actualiza el estado con memory_context, que luego consume la generación. limit=5 es el k: más contexto vs. más tokens y ruido.
Documents

La colección memories

El store guarda cada recuerdo como un documento JSON con namespace, key y value. Con index_config, agrega el embedding para la búsqueda semántica.

namespace + key + value (+ embedding) = un recuerdo recuperable.
{
  "namespace": ["68412097", "memories"],
  "key": "b1f2c3d4-...",
  "value": { "data": "Le encanta Star Wars" },
  "created_at": "2026-09-30T...",
  "updated_at": "2026-09-30T..."
}
Muestra en vivo (si puedes) un documento real. El namespace es un array (user_id, "memories"). El embedding no se ve en el value: el store lo calcula y lo guarda aparte para el índice vectorial.
Generación

Nodo de generación de respuesta

La memoria de largo plazo se inserta junto con los mensajes del estado (memoria de corto plazo) para entregar una respuesta coherente.

1 · Recuperar memoria y chain
async def generate_response(state: StateBot, config: RunnableConfig):
    memory_context = state.get('memory_context')
    chain = get_character_chain()
2 · Invocar con ambas memorias
    response = await chain.ainvoke(
        {
            "messages": state['messages'],
            "memory_context": memory_context,
        },
        config,
    )
    return {"messages": response}
Corto plazo (mensajes) + largo plazo (memory_context) = respuesta con contexto.
Aquí se juntan las dos memorias: la lista de mensajes (hilo) y el contexto recuperado (hechos). El character chain recibe ambos y responde en personaje.
Lo que nadie te cuenta

El costo de recordar

Cada mensaje del usuario dispara trabajo extra además de la respuesta.

+1 llamada al LLM
Memory chain

Analiza si el mensaje merece guardarse. Es una llamada adicional por mensaje.

+1 embedding
Vectorizar

El store lo calcula al hacer put; es una llamada al modelo de embeddings.

+1 búsqueda vectorial
limit=5

Recuperar los recuerdos relevantes antes de responder.

Mitigaciones: extraer solo si is_important, cachear embeddings, acotar el limit y usar TTL/prune. La memoria no es gratis, pero se paga sola.
Slide de honestidad técnica: la memoria añade latencia y costo. Explica las mitigaciones. Este es el punto que suele generar las mejores preguntas.

Lo que aprendí

Gotchas de la memoria persistente

Privacidad
PII en la DB

Estás guardando datos personales. Define qué se guarda, por cuánto y cómo se borra.

Duplicados
Sin dedup

El mismo hecho puede guardarse muchas veces. Normaliza o deduplica.

Aislamiento
user_id / namespace

Sin namespace por usuario, los recuerdos se mezclan entre conversaciones.

Checkpoints
Crecen sin parar

MongoDB soporta ttl y prune nativos: úsalos en lugar de limpiar a mano.

Embeddings
Cambiar = reconstruir

Otro modelo o dimensión invalida el índice vectorial existente.

Errores silenciosos
try/except

Devolver vacío ante un fallo evita romper, pero oculta el problema: loguea.
