01

Fundamentos web

Qué es una API REST y por qué el mundo habla HTTP

⏱ 10 s · Divisor. Recordar que REST no es una tecnología sino un conjunto de convenciones.
Punto de partida

¿Qué es una API REST?

API
Contrato

Interfaz que permite que dos programas se comuniquen: el cliente pide, el servidor responde.

REST
Convenciones

REpresentational State Transfer: reglas para diseñar esos servicios de forma uniforme sobre HTTP.

i
Se apoya en el protocolo HTTP y se usa en casi toda aplicación web moderna: móviles, frontends, microservicios.
⏱ 90 s · Definir API y REST con la analogía del restaurante: el menú es el contrato, el mesero es HTTP. No entrar aún en verbos ni códigos.
Característica 1

Recursos y endpoints

Todo se modela como un recurso: una entidad con nombre. Cada recurso vive en una URL única.

/productos la colección de productos
/productos/42 un producto concreto
/pedidos/42/items los ítems de un pedido
✓
Nombra recursos con sustantivos en plural (productos), no con acciones (obtenerProductos).
⏱ 90 s · El endpoint es la URL. La jerarquía /pedidos/42/items muestra relaciones. Regla práctica: sustantivos, plural, minúsculas.
Característica 2

Verbos HTTP

La acción no va en la URL: va en el método HTTP.

GET leer / recuperar datos
POST crear un recurso nuevo
PUT reemplazar un recurso completo
PATCH actualizar parcialmente
DELETE eliminar un recurso
GET /productos?categoria=ropa
i
Mismo endpoint /productos, distinto verbo: GET lo lista, POST lo crea.
⏱ 120 s · Insistir en la separación acción/recurso. PUT vs PATCH es la duda clásica: reemplazo total vs parcial.
Característica 3

Sin estado y en JSON

stateless
Sin estado

Cada petición lleva toda la información necesaria (incluida la identidad). El servidor no recuerda al cliente entre peticiones.

formato
JSON

Los datos viajan en un formato estándar: application/json. Fácil de leer por humanos y máquinas.

respuesta típica
{
  "id": 42, "nombre": "Mouse", "precio": 25.9, "en_stock": true
}
⏱ 90 s · Stateless habilita escalar horizontalmente: cualquier servidor puede atender cualquier petición. JSON es el idioma franco actual.
Característica 4

Códigos de estado

HTTP responde con un número que cuenta qué pasó. Se agrupan por familia.

2xx
Éxito. 200 OK · 201 Created · 204 No Content
3xx
Redirección. 301 Moved · 304 Not Modified
4xx
Error del cliente. 400 · 401 · 403 · 404 · 422
5xx
Error del servidor. 500 · 503
!
El 422 es la estrella de FastAPI: datos válidos como JSON pero que no cumplen el esquema.
⏱ 120 s · No memorizar todos: entender familias. 4xx culpa del cliente, 5xx culpa del servidor. El 422 se usará en la validación con Pydantic.
Por qué REST

Ventajas para el desarrollo

Desacople

Frontend y backend evolucionan por separado; pueden vivir en servidores distintos.

Escalable

Sin estado: se replican servidores y balanceadores con facilidad.

Universal

Independiente del lenguaje y la plataforma del cliente o del servidor.

✓
Un mismo backend sirve a la web, a la app móvil y a otros servicios internos.
⏱ 60 s · Cerrar la parte teórica conectando con FastAPI: un framework que hace estas convenciones fáciles de implementar.
02

FastAPI

El framework moderno para construir APIs con Python

⏱ 10 s · Divisor. Prometer: en pocas líneas ya tendremos una API con documentación incluida.
El framework

¿Qué es FastAPI?

Un framework web moderno y de alto rendimiento para construir APIs con Python 3.10+, basado en las anotaciones de tipos del lenguaje.

velocidad
ASGI

Asíncrono de verdad, comparable a Node.js y Go.

tipado
Type hints

Los tipos son la fuente de verdad: validación y docs salen de ahí.

adopción
Empresas

Usado por Microsoft, Uber, Netflix y miles de equipos.

⏱ 90 s · Enfatizar que FastAPI no inventa un lenguaje: aprovecha el tipado de Python. Eso es lo que lo hace distinto a Flask o Django para APIs.

Los tres son Python. FastAPI brilla cuando el contrato de la API y el rendimiento son la prioridad.
⏱ 90 s · No es "el mejor", es "el más adecuado para APIs". Django sigue siendo gran opción si necesitas admin, ORM y baterías incluidas.

Arquitectura

Sobre hombros de gigantes

FastAPI es una capa delgada y bien pensada sobre dos bibliotecas maduras.

web
Starlette

Toolkit ASGI (el sucesor de WSGI) para las partes web: rutas, peticiones, respuestas, WebSockets.

datos
Pydantic

Validación y serialización de datos basada en tipos. El corazón del tipado de FastAPI.

✓
Entender estas dos piezas hace que FastAPI deje de ser magia y pase a ser predecible.
⏱ 90 s · Starlette = web, Pydantic = datos. Cada mensaje de error de validación viene de Pydantic; cada respuesta y middleware viene de Starlette.

La base de todo

Type hints

Todo FastAPI se apoya en las anotaciones de tipo de Python. No son obligatorias, pero lo cambian todo.

sin tipos
nombre = "Mouse"
precio = 25.9
en_stock = True
con tipos (moderno)
nombre: str = "Mouse"
precio: float = 25.9
en_stock: bool = True
i
Desde Python 3.9+ se usan los genéricos nativos: list[str], dict[str, int]. Y desde 3.10, str | None en lugar de Optional[str].
⏱ 90 s · Mostrar que list[str] reemplaza a typing.List[str]. Este cambio moderno es una de las actualizaciones clave frente a las charlas antiguas.

Datos en la URL

Parámetros de ruta

Un segmento variable se declara entre llaves y llega como argumento de la función.

main.py
@app.get("/productos/{producto_id}")
async def obtener_producto(producto_id: int):
    return {"producto_id": producto_id}
i
Al pedir /productos/42, FastAPI llama a la función con producto_id=42.
⏱ 90 s · El nombre entre llaves debe coincidir con el argumento. Es la primera vez que aparece un dato dinámico.
Validación gratis

Parámetros con tipos

Declarar el tipo activa el parseo y la validación automáticos.

main.py
@app.get("/productos/{producto_id}")
async def obtener(producto_id: int):
    return {"producto_id": producto_id}
✓
/productos/42 → 200 OK, producto_id es un int.
×
/productos/abc → 422 con un error explicando el tipo.
⏱ 90 s · Aquí se ve el valor del tipado: no escribimos validación manual. Mostrar el JSON de error de Pydantic si se puede.
Valores predefinidos

Enum: valores permitidos

Cuando un parámetro solo admite ciertos valores, usa Enum.

main.py
from enum import Enum

class Categoria(str, Enum):
    electronica = "electronica"
    ropa = "ropa"
    hogar = "hogar"

@app.get("/productos/categoria/{categoria}")
async def por_categoria(categoria: Categoria):
    return {"categoria": categoria}
✓
La documentación mostrará un desplegable con las opciones válidas. Cualquier otro valor da 422.
⏱ 90 s · Enum convierte reglas de negocio en tipos. Heredar de str hace que el valor serialice como texto en el JSON.
Datos en la query

Parámetros de consulta

Van después del ? en la URL, separados por &. Se usan para filtrar, paginar u ordenar.

URL
GET /productos?skip=0&limit=10
main.py
@app.get("/productos")
async def listar_productos(skip: int = 0, limit: int = 10):
    return productos[skip : skip + limit]
i
Todo argumento que no está en el path y tiene un tipo simple se interpreta como parámetro de consulta.
⏱ 120 s · Diferencia clave path vs query: path identifica el recurso, query lo modula. skip/limit es el patrón clásico de paginación.
Tres casos

Por defecto, opcional o requerido

por defecto
skip: int = 0
limit: int = 10
opcional
q: str | None = None
requerido
q: str
i
Si no se envía, toma el valor por defecto.
i
Puede faltar; llega como None.
!

✓
Regla de oro: sin valor por defecto = requerido.
⏱ 120 s · Este trío se pregunta siempre. Insistir: la ausencia de default es lo que marca "requerido". Mostrar str | None como reemplazo moderno de Optional[str].
Reglas declarativas

Validación en parámetros

Con Query y Path añades restricciones que se validan y aparecen en /docs.

main.py
from fastapi import Path, Query

@app.get("/productos")
async def listar(
    skip: int = Query(0, ge=0),
    limit: int = Query(10, ge=1, le=100),
    q: str | None = Query(None, min_length=2),
):
    ...

@app.get("/productos/{producto_id}")
async def obtener(producto_id: int = Path(gt=0)):
    ...
✓
ge/le (rangos) y min_length se validan solos: fuera de rango → 422.
⏱ 120 s · La validación no es solo de tipos sino de reglas. Todo queda documentado en Swagger sin esfuerzo adicional.
Enviar datos

Request body con Pydantic

Los datos que envía el cliente se modelan con una clase de Pydantic.

main.py
from pydantic import BaseModel, Field

class ProductoCreate(BaseModel):
    nombre: str
    descripcion: str | None = None
    precio: float = Field(gt=0)
    en_stock: bool = True

@app.post("/productos")
async def crear_producto(producto: ProductoCreate):
    return producto
i
FastAPI lee el JSON, lo convierte, lo valida y te entrega un objeto ProductoCreate listo para usar.
⏱ 150 s · Aquí está el superpoder. Field(gt=0) es una regla declarativa. El mismo modelo alimenta la validación y la documentación.
Cuando los datos no cuadran

Validación automática

Si el cuerpo no cumple el esquema, FastAPI responde 422 con el detalle exacto.

enviamos
{
  "nombre": "Mouse", "precio": -5
}
respuesta 422
{
  "detail": [{
    "loc": ["body", "precio"],
    "msg": "Input should be greater than 0"
  }]
}
✓
No escribimos ni un if: la regla vive en el modelo y el error indica campo y motivo.
⏱ 120 s · Este es el gran diferenciador frente a validar a mano. Mostrar que el mensaje dice el campo exacto (loc) y por qué falló.
Todo junto

Body + path + query

FastAPI decide de dónde tomar cada parámetro según su tipo y su nombre.

main.py
@app.put("/productos/{producto_id}")
async def actualizar(
    producto_id: int,
    producto: ProductoCreate,
    notificar: bool = False,
):
    return {"id": producto_id, **producto.model_dump()}
i
producto_id → viene del path.
i
producto (Pydantic) → del body.
i
notificar (simple) → de la query.
⏱ 120 s · Regla mental: path si está en la URL, body si es un modelo Pydantic, query si es un tipo simple. model_dump() reemplaza al antiguo .dict() de Pydantic v2.
Controlar la salida

response_model

Define qué se devuelve. FastAPI filtra los campos que no estén en el modelo de salida.

main.py
class UsuarioIn(BaseModel):
    username: str
    password: str

class UsuarioOut(BaseModel):
    username: str

@app.post("/usuarios", response_model=UsuarioOut)
async def crear_usuario(usuario: UsuarioIn):
    return usuario  # la contraseña nunca se expone
×
Nunca devuelvas el modelo de entrada si contiene datos sensibles: usa un modelo de salida.
⏱ 120 s · Caso real de seguridad: entrada y salida son modelos distintos. FastAPI descarta los campos extra automáticamente.
Comunicar el resultado

Códigos de estado explícitos

Por defecto todo responde 200. Indica el código correcto con status_code.

main.py
from fastapi import status

@app.post("/productos", status_code=status.HTTP_201_CREATED)
async def crear_producto(producto: ProductoCreate):
    return producto
201 recurso creado
204 sin contenido (DELETE)
⏱ 90 s · Usar las constantes status.HTTP_* en vez de números mágicos. Es parte de un buen contrato de API.
Errores con sentido

Errores y HTTPException

Para errores de negocio, lanza una excepción con su código HTTP.

main.py
from fastapi import HTTPException

@app.get("/productos/{producto_id}", response_model=ProductoOut)
async def obtener(producto_id: int, db: AsyncSession = Depends(get_db)):
    producto = await db.get(Producto, producto_id)
    if producto is None:
        raise HTTPException(status_code=404, detail="Producto no encontrado")
    return producto
i
FastAPI convierte la excepción en {"detail": "..."} con el código indicado. Puedes unificar el formato con @app.exception_handler.
⏱ 120 s · 404 para "no existe", 400 para datos inválidos de negocio, 403 para prohibido. Un handler global unifica el formato de error.
Para no tropezar

Errores comunes

×
Olvidar async o el tipo en un parámetro: pierdes validación y docs.
×
Devolver el modelo de entrada con la contraseña incluida.
×
Usar .dict() (Pydantic v1) en vez de .model_dump().
×
Bloquear el event loop con código síncrono pesado dentro de async def.
×
Confundir path y query: si está en la URL es path; si es filtro, query.
×
No declarar response_model y filtrar datos sensibles.
⏱ 120 s · Repaso activo: preguntar a la audiencia por qué cada uno es un error. Es el resumen del bloque 04.

Dependencias y tareas en segundo plano

⏱ 10 s · Divisor. Dos patrones que separan una demo de una app real.
Patrón clave

Inyección de dependencias

Una dependencia es una función que FastAPI resuelve y entrega a tu ruta automáticamente.

Reutilizar

Defines una vez y la usas en muchas rutas.

Testear

Fácil de reemplazar por una versión de prueba.

Ordenar

Separa la lógica de las operaciones externas.

✓
La usaremos para paginación, conexión a la base de datos y el usuario autenticado.
⏱ 90 s · No es magia: FastAPI mira las dependencias declaradas y las resuelve antes de llamar a la función. Anticipar que es la misma herramienta para get_db y get_current_user.
En código

Una dependencia en acción

main.py
from fastapi import Depends

def paginacion(skip: int = 0, limit: int = 10):
    return {"skip": skip, "limit": limit}

@app.get("/productos")
async def listar(pag: dict = Depends(paginacion)):
    return pag
i
Depends(paginacion) le dice a FastAPI: resuelve esa función (incluidos sus query params) y pásame el resultado.
⏱ 120 s · Mostrar que la dependencia puede tener sus propios parámetros de query, que también aparecen en /docs. Composición de dependencias es el siguiente paso natural.
Trabajo diferido

Tareas en segundo plano

Para cosas que deben pasar después de responder: correos, notificaciones, logs.

main.py
from fastapi import BackgroundTasks

def enviar_correo(email: str, mensaje: str):
    ...

@app.post("/pedidos")
async def crear_pedido(email: str, background_tasks: BackgroundTasks):
    background_tasks.add_task(enviar_correo, email, "Pedido confirmado")
    return {"estado": "creado"}
✓
El cliente recibe la respuesta al instante; el correo se envía después, sin bloquearlo.
⏱ 120 s · Aclarar que corre en el mismo proceso tras enviar la respuesta. Sirve para trabajo ligero; para pesado, ver la siguiente slide.
Combinando patrones

BackgroundTasks + dependencias

BackgroundTasks también funciona dentro de una dependencia; todas las tareas se fusionan y se ejecutan juntas al final.

main.py
def auditar(background_tasks: BackgroundTasks, q: str | None = None):
    if q:
        background_tasks.add_task(registrar_busqueda, q)
    return q

@app.get("/productos")
async def listar(q: str = Depends(auditar)):
    return {"q": q}
i
Se pueden declarar tareas en la ruta, en una dependencia o en una subdependencia: FastAPI reutiliza el mismo objeto.
⏱ 90 s · Patrón útil para auditoría. Enfatizar que el mismo BackgroundTasks circula por toda la cadena de dependencias.
Límites

¿Y si la tarea es pesada?

background tasks
Simple

Mismo proceso, tras la respuesta. Ideal para correos, notificaciones y logs.

cola de tareas
Celery / RQ

Otro proceso, con broker (Redis/RabbitMQ). Para trabajo pesado, reintentos y varios servidores.

!
Si la tarea puede tardar minutos o debe sobrevivir a un reinicio, usa una cola, no BackgroundTasks.
⏱ 90 s · Criterio de decisión, no dogmatismo. BackgroundTasks cubre el 80% de los casos; las colas son para lo serio.

Datos y seguridad

Base de datos y autenticación

⏱ 10 s · Divisor. Aquí la API deja de tener datos en memoria y se vuelve una app real.
12-factor

Configuración por entorno

Nada de secretos en el código: se leen del entorno con pydantic-settings.

config.py
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    database_url: str
    secret_key: str
    model_config = SettingsConfigDict(env_file=".env")

settings = Settings()
!
Instala pip install pydantic-settings. Añade .env a .gitignore.
⏱ 90 s · Mismo código en dev, staging y prod; solo cambian las variables. Es la base de la metodología 12-factor.
Persistencia

Base de datos con SQLAlchemy

SessionLocal = async_sessionmaker(engine, expire_on_commit=False)

    pass
i

Arranque y cierre

Ciclo de vida: lifespan

Recursos que se abren al arrancar la app y se cierran al apagarla.

main.py
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    await conectar_recursos()
    yield
    await liberar_recursos()

app = FastAPI(lifespan=lifespan)
✓
Reemplaza a los antiguos eventos startup/shutdown. Ideal para pools de conexión y clientes HTTP.
⏱ 90 s · Todo lo que ocurre antes del yield es arranque; después, cierre. Evita abrir conexiones en cada petición.
Dos capas

Modelo ORM vs esquema Pydantic

models.py · tabla
from sqlalchemy.orm import Mapped, mapped_column
from database import Base

class Producto(Base):
    __tablename__ = "productos"
    id: Mapped[int] = mapped_column(primary_key=True)
    nombre: Mapped[str]
    precio: Mapped[float]
schemas.py · API
from pydantic import BaseModel, ConfigDict

class ProductoOut(BaseModel):
    id: int
    nombre: str
    precio: float
    model_config = ConfigDict(from_attributes=True)
✓
El modelo ORM describe la tabla; el esquema Pydantic describe lo que entra y sale por la API. No los mezcles.
⏱ 150 s · Punto que más confunde. from_attributes=True es el reemplazo moderno de orm_mode=True en Pydantic v2: permite leer atributos del objeto ORM.
Conectar todo

Dependencia de sesión y CRUD

main.py
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

async def get_db():
    async with SessionLocal() as db:
        yield db

@app.get("/productos", response_model=list[ProductoOut])
async def listar(db: AsyncSession = Depends(get_db)):
    result = await db.scalars(select(Producto))
    return result.all()
i
get_db usa yield: abre la sesión, la entrega y la cierra al terminar. Y con async with + await no bloquea el event loop.
!
Si usas SQLAlchemy síncrono, declara la ruta con def (no async def): FastAPI la ejecuta en un threadpool y evita bloquear el loop.
⏱ 150 s · El patrón yield garantiza el cierre de la sesión. list[ProductoOut] combina tipado moderno con response_model. La sesión se inyecta igual que cualquier dependencia.

Proteger la API

Autenticación y autorización

Autenticar es saber quién eres; autorizar es saber qué puedes hacer.

security.py
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")
i
El esquema OAuth2 dice que el token se obtiene en /token. FastAPI lo usa para pedir el header Authorization: Bearer ... y mostrarlo en /docs.
⏱ 120 s · Distinguir autenticación de autorización. OAuth2PasswordBearer solo describe cómo llega el token; la verificación la haremos en la dependencia.
La dependencia de usuario

get_current_user

security.py
from fastapi import HTTPException

async def get_current_user(token: str = Depends(oauth2_scheme)):
    usuario = decodificar_token(token)  # verifica firma y expiración
    if usuario is None:
        raise HTTPException(
            status_code=401,
            detail="Token inválido",
            headers={"WWW-Authenticate": "Bearer"},
        )
    return usuario

@app.get("/usuarios/me")
async def perfil(usuario: Usuario = Depends(get_current_user)):
    return usuario
×
En producción usa tokens JWT firmados (python-jose / PyJWT) y contraseñas con hash (passlib/bcrypt). Nunca guardes contraseñas en texto plano.
⏱ 150 s · Una sola dependencia protege todas las rutas que la declaren. El 401 es la respuesta correcta para token ausente o inválido.

    return "asyncio"
