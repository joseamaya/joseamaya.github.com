01

REST

Qué es una API REST y qué restricciones sigue.

⏱ 15 s · Sección de conceptos. Lo justo para entender las decisiones de DRF.
Punto de partida

¿Qué es una API REST?

2000

Roy Fielding describe REST en su tesis doctoral: uno de los padres de la especificación HTTP.

≠ arquitectura

No es una arquitectura de software: es un conjunto de restricciones para diseñar un estilo de arquitectura.

JSON / XML

Una interfaz entre sistemas que usa HTTP para obtener datos u operar sobre ellos.

⏱ 2 min · REST = Representational State Transfer. Insistir en que es un estilo con restricciones, no una tecnología ni un protocolo. HTTP ya nos da casi todo.
Restricciones

Características de REST (I)

Cliente-servidor

Débilmente acoplados: el cliente no conoce la implementación del servidor y viceversa. Pueden evolucionar por separado.

Interfaz uniforme

Cada recurso tiene una única dirección: su URI. /cursos/, /cursos/3/…

Operaciones

POST crear · GET leer · PUT editar · DELETE eliminar.

⏱ 2 min · Los verbos HTTP son las operaciones sobre recursos. Una URI = un recurso; el verbo indica qué hacer con él. Esto es exactamente lo que DRF mapea a vistas.
Restricciones

Características de REST (II)

Sin estado

Cada petición es independiente: el servidor no necesita recordar sesiones. Todo lo necesario viaja en la petición.

Cacheable

Las respuestas deben poder marcarse como cacheables para evitar trabajo repetido.

Sistema de capas

El servidor puede implementarse en capas: balanceadores, cachés, proxies… el cliente no necesita saberlo.

⏱ 1.5 min · Sin estado ≠ sin base de datos: el estado vive en el cliente o en la BD, no en la sesión del servidor. Las capas permiten escalar.
La idea en una imagen

Cliente, métodos y servidor

⏱ 2 min · Recorrer el diagrama de izquierda a derecha. El cliente y el servidor solo comparten el contrato: métodos, URIs y formato. La base de datos es un detalle interno del servidor.
Vocabulario HTTP

Métodos y códigos de estado

Métodos
GETLeer un recurso o una colección
POSTCrear un recurso
PUTReemplazar un recurso completo
PATCHActualizar parte de un recurso
DELETEEliminar un recurso
Códigos frecuentes
200OK · la operación salió bien
201Created · recurso creado
400Bad Request · datos inválidos
404Not Found · no existe
500Server Error · fallo del servidor
⏱ 2 min · DRF traduce automáticamente: POST que crea → 201, validación fallida → 400, recurso inexistente → 404. No hay que escribirlos a mano.
Por qué REST

Ventajas para el desarrollo

Separación cliente-servidor

Frontend y backend en servidores distintos, con equipos y ciclos independientes. La interfaz es la API.

Visibilidad, fiabilidad y escalabilidad

Puedes migrar servidores o cambiar la base de datos sin tocar al cliente, mientras se respete el contrato.

Independiente de la plataforma

La misma API la consumen una web, una app móvil, otro servicio o una integración.

Un contrato claro

Recursos, métodos y códigos de estado: cualquiera puede integrarse sin leer tu código.

⏱ 1.5 min · Conectar con el día a día: el mismo backend sirve a la web, al móvil y a futuras integraciones. DRF hace esto casi gratis.

Django y DRF

El framework web y su toolkit para APIs.

⏱ 15 s · Puente: ya sabemos qué queremos construir; ahora con qué.
El framework

¿Qué es Django?

Baterías incluidas

ORM, autenticación, admin, formularios, plantillas y migraciones: listo para producción.

Apps reutilizables

Un proyecto se compone de aplicaciones con una responsabilidad cada una: cursos, usuarios…

ORM

Clases Python que se reflejan en tablas de la base de datos, sin escribir SQL a mano.

✓
Django 5.2 LTS: soporte extendido y la versión que usarás en proyectos reales. Todo lo que veamos aplica igual en 4.2+.
⏱ 2 min · Django es el framework full-stack de Python por excelencia. Para esta charla nos interesan dos piezas: el ORM (modelos) y las URLs/vistas. El resto no lo usaremos hoy.

El toolkit

Django REST Framework

Una app de Django para construir APIs REST reutilizando piezas, con una API navegable desde el navegador.

Serialización

Convierte modelos (y otros orígenes) a JSON y valida lo que entra: como los Forms, pero para APIs.

Vistas y routers

Vistas genéricas y ViewSets que implementan un CRUD completo con muy poco código.

Autenticación y permisos

Integración con sesiones, OAuth1a/2, tokens y JWT; permisos declarados por vista.

Comunidad y docs

Documentación excelente y uso intensivo en producción (Mozilla, Red Hat, Heroku…).

⏱ 2.5 min · DRF es a Django lo que Django es a Python: convenciones y piezas listas. Destacar la API navegable: podremos probar el CRUD en el navegador sin Postman ni curl.
La diferencia

¿Por qué no con vistas Django a mano?

No es que no se pueda: es que con DRF escribes menos código y ganan consistencia los errores, la paginación y los permisos.
⏱ 1.5 min · Comparación honesta: en una app clásica puedes devolver JsonResponse, pero acabas reimplementando validación, códigos de estado y paginación. DRF da todo eso con convenciones.

04

El CRUD

Modelos, serializadores, vistas y routers.

⏱ 15 s · El corazón de la charla: cuatro piezas y un CRUD completo.
Pieza 1

Los modelos

  • Descripciónlos datos, en código Python, reflejados en tablas de la base de datos.
  • SQL por detráscada consulta ejecuta SQL y devuelve objetos Python cómodos de usar.
  • models.pycada aplicación declara ahí sus modelos.
✓
Nuestro dominio: Categoria y Curso, con una relación de muchos a muchos y un creador.
⏱ 1.5 min · Un modelo es una clase = una tabla. Cada atributo = una columna. Las migraciones traducen los cambios del modelo a la base de datos.
Pieza 1

models.py

cursos/models.py
from django.contrib.auth.models import User
from django.db import models


class Categoria(models.Model):
    nombre = models.CharField(max_length=20)


class Curso(models.Model):
    titulo = models.CharField(max_length=100)
    descripcion = models.TextField(blank=True)
    categorias = models.ManyToManyField(Categoria, related_name="cursos")
    creador = models.ForeignKey(
        User, on_delete=models.CASCADE, null=True, blank=True
    )

    def __str__(self):
        return self.titulo
i
Cambios frente al original: on_delete es obligatorio desde Django 2.0, related_name="cursos" es más claro y agregamos __str__.
⏱ 3 min · Recorrer el código con calma. on_delete define qué pasa con los cursos si se borra el usuario creador. __str__ hace legible el modelo en el admin. Tras editar el modelo: makemigrations + migrate.
Pieza 2

Los serializadores

Convierten objetos Python ⇄ JSON y validan lo que entra, como los Forms.

Serializercontrol total: defines cada campo a mano
ModelSerializerinfiere campos y validaciones del modelo
serializers.pyconvención de DRF para declararlos
⏱ 2 min · Serializar = objeto → JSON para responder; deserializar = JSON → objeto validado para guardar. ModelSerializer evita repetir el modelo: DRF genera los campos y sus validaciones.
Pieza 2

serializers.py

cursos/serializers.py
from rest_framework import serializers

from cursos.models import Categoria, Curso


class CategoriaSerializer(serializers.ModelSerializer):
    class Meta:
        model = Categoria
        fields = ("id", "nombre")


class CursoSerializer(serializers.ModelSerializer):
    class Meta:
        model = Curso
        fields = ("id", "titulo", "descripcion", "categorias", "creador")
i
En producción marca creador como read_only_fields y asígnalo desde self.request.user: nadie debería crear cursos a nombre de otro.
⏱ 2.5 min · fields decide qué se expone y qué se acepta. Fíjate que añadimos "id" al CursoSerializer, que el original omitía. ModelSerializer también valida longitudes y tipos a partir del modelo.
Pieza 3

Las vistas

  • Entradareciben un objeto con la información de la petición (request).
  • Salidadevuelven JSON (u otro formato) o una excepción si algo falla.
  • views.pycada aplicación declara ahí sus vistas; en DRF suelen ser clases.
✓
DRF trae vistas genéricas que ya implementan listar, crear, recuperar, actualizar y borrar.
⏱ 1.5 min · Una vista es el punto donde la petición aterriza. Con DRF heredamos de clases que ya saben hacer el CRUD: solo conectamos queryset y serializer.
Pieza 3

La jerarquía de vistas de DRF

APIViewcontrol total: escribes cada get(), post() a mano
GenericAPIView+ queryset, serializer_class, get_object()
ListCreateAPIViewlistar + crear
RetrieveUpdateDestroyAPIViewdetalle + editar + borrar

i
Cuanto más abajo, menos código escribes y más convenciones aceptas. Puedes bajar de nivel cuando lo necesites.
⏱ 2 min · No hay que memorizar la jerarquía: entender que existen niveles. APIView para control total; las genéricas para CRUD por recurso; ModelViewSet cuando quieres el CRUD completo con router.

Pieza 3

views.py

cursos/views.py
from rest_framework import viewsets

from cursos.models import Categoria, Curso
from cursos.serializers import CategoriaSerializer, CursoSerializer


class CategoriaViewSet(viewsets.ModelViewSet):
    queryset = Categoria.objects.all()
    serializer_class = CategoriaSerializer


class CursoViewSet(viewsets.ModelViewSet):
    queryset = Curso.objects.all()
    serializer_class = CursoSerializer
!
Error clásico: en el taller original los queryset estaban cruzados (CategoriasView consultaba Curso). Cada vista debe apuntar a su propio modelo.
⏱ 3 min · Cada ViewSet son dos atributos: qué consultar y cómo serializarlo. Ese es todo el CRUD. Contar la anécdota del bug del taller original y cómo se detecta (el endpoint devolvía el modelo equivocado).

Pieza 4

Los routers

  • Definir URLsgeneran las rutas del API de forma ordenada a partir de los ViewSets.
  • Mapear verbosdeciden qué acción se ejecuta según el verbo HTTP y el path.
  • Organizartodo en el urls.py del proyecto o uno por aplicación.
✓
Con DefaultRouter registramos cursos una vez y obtenemos las 6 rutas del CRUD, sin escribir ningún path() a mano.
⏱ 1.5 min · Router = convención sobre URLs. registrar("cursos", CursoViewSet) genera /cursos/ y /cursos/{id}/ y asocia GET/POST/PUT/PATCH/DELETE a las acciones que vimos.
Pieza 4

urls.py

taller/urls.py
from django.contrib import admin
from django.urls import include, path
from rest_framework import routers

from cursos.views import CategoriaViewSet, CursoViewSet

router = routers.DefaultRouter()
router.register("cursos", CursoViewSet, basename="cursos")
router.register("categorias", CategoriaViewSet, basename="categorias")

urlpatterns = [
    path("admin/", admin.site.urls),
    path("api/v1/", include(router.urls)),
]
i
Del taller original a hoy: url() con regex pasó a path(), y la API se monta bajo /api/v1/ para poder versionarla.
⏱ 2.5 min · El router se registra una vez por recurso. El prefijo /api/v1/ versiona desde el día uno. El original definía una variable URL_API_BASE_V1 que luego no usaba: aquí lo hacemos bien.

Aprendiendo de los errores

Errores comunes

Querysets cruzados

CategoriaViewSet debe usar Categoria.objects.all(), no Curso. Síntoma: el endpoint devuelve datos del otro modelo.

Falta on_delete

Obligatorio en cada ForeignKey desde Django 2.0. Y si cambias el modelo: makemigrations + migrate.

Olvidar rest_framework

Sin registrarlo en INSTALLED_APPS no hay API navegable ni routers.

Rutas sin prefijo

Montar la API en /api/v1/ desde el inicio te deja evolucionar sin romper clientes.

⏱ 2 min · El primero salió del taller original: los querysets estaban intercambiados. Los demás son los que vemos en code review: migraciones olvidadas y APIs sin prefijo ni versionado.
