Fundamentos

Tenants, aislamiento y PostgreSQL schemas

⏱ 10 s · Divisor. Primero entender el problema antes de tocar código.
Vocabulario

¿Qué es un tenant?

tenant
Inquilino

Un cliente lógico cuyos datos deben mantenerse separados del resto. En AulaSaaS, cada colegio.

multitenancy
Compartir

Una sola instalación atiende a muchos tenants, compartiendo infraestructura pero aislando datos.

i
La clave no es "muchos clientes", sino cómo separas sus datos. De eso salen los 3 patrones.
⏱ 90 s · Distinguir tenant (concepto de negocio) de la técnica usada para aislarlo. El resto del bloque trata sobre las técnicas.
El problema

SaaS multiempresa

Sin un modelo claro aparecen dos extremos, y ambos duelen.

si comparto todo
Una sola tabla

Filtros manuales (where tenant_id=...) en cada query. Un olvido = una fuga entre colegios.

si aíslo todo
Una BD por cliente

Aislamiento perfecto, pero el coste y la operación se multiplican por cada tenant.

!
El objetivo es el punto medio: aislamiento fuerte sin multiplicar la operación.
⏱ 90 s · Plantear el dilema aislamiento vs coste. Toda la charla es una respuesta a este trade-off.
Las tres opciones

Los 3 patrones de multitenancy

1 · compartido
Shared schema

Una BD, un schema. Cada tabla lleva tenant_id. Máximo ahorro, máximo riesgo.

2 · por schema
Schema-per-tenant

Una BD, un schema por tenant. Aislamiento fuerte y buena eficiencia. El enfoque de esta charla.

3 · por base
Database-per-tenant

Una BD por cliente. Aislamiento total; coste y operación altos.

✓
PostgreSQL es ideal para el patrón 2: los schemas son como carpetas dentro de la misma base de datos.
⏱ 150 s · Nombres canónicos (los mismos de la doc de django-tenants y del artículo de Microsoft). El patrón 2 es el "punto medio" que perseguimos.
Elegir con criterio

Comparativa

Shared schemaSchema-per-tenantDB-por-tenant
AislamientoBajo (filtros)AltoTotal
CosteMínimoBajoAlto
ComplejidadBajaMediaAlta
MigracionesUnaPor schemaPor base

⏱ 120 s · No hay patrón único. Para B2B con clientes que exigen sus datos separados, schema-per-tenant es el balance habitual.
Decisión

Cómo elegir

Nº de tenants cientos o miles → schema-per-tenant
Aislamiento requisito legal fuerte → DB-por-tenant
Datos comunes catálogos globales → schema public
Equipo pequeño → minimiza la operación
Personalización por cliente → favorece separar
Coste prioridad → shared schema + RLS
i
Y siempre: puedes migrar después. Empezar compartido y pasar a schemas es más fácil que al revés.
⏱ 90 s · Herramienta de decisión, no dogma. Pedir al público su caso y elegir en voz alta.
La pieza clave

PostgreSQL schemas

Un schema es un espacio de nombres dentro de una base de datos: permite repetir el nombre de tabla sin conflictos.

public schema por defecto, ideal para lo compartido
acme.cursos y gea.cursos son tablas distintas
search_path indica en qué schemas buscar las tablas
✓
Con search_path = acme, public el ORM consulta acme primero y cae a public para lo compartido.
⏱ 120 s · La analogía de la carpeta: mismo nombre de archivo en carpetas distintas. search_path es el "directorio actual" de la base de datos.

Si compartes schema

Row-Level Security

Si eliges shared schema, no confíes solo en el filtrado del ORM: refuérzalo en la base de datos.

rls.sql
ALTER TABLE cursos ENABLE ROW LEVEL SECURITY;

CREATE POLICY aislamiento ON cursos
  USING (tenant_id = current_setting('app.tenant_id')::int);
✓
Postgres aplica el filtro por ti: aunque una query olvide el WHERE, no devuelve datos de otro tenant.
⏱ 120 s · RLS es la red de seguridad del patrón compartido. En schema-per-tenant el aislamiento ya lo da el search_path.
El riesgo real

Fugas de datos entre tenants

×
Un WHERE tenant_id=... olvidado en shared schema.
×
Un search_path mal fijado que apunta al schema equivocado.
×
Un dominio que resuelve al tenant incorrecto.
×
Caché o archivos servidos sin segmentar por tenant.
!
Una fuga entre clientes de una plataforma B2B suele ser el peor incidente posible: legal, económico y reputacional.
⏱ 90 s · El aislamiento no es un detalle técnico, es el requisito de negocio número uno. Volveremos a esto en seguridad.

django-tenants

Schema por tenant en Django, de la teoría al código

⏱ 10 s · Divisor. Del concepto a la implementación.
La librería

Qué es django-tenants

El paquete de referencia para multitenancy con schemas de PostgreSQL en Django.

Activo

Fork mantenido por la comunidad. Compatible con Django 5 y psycopg 3.

Transparente

Casi no cambias tu código: el schema se fija por petición.

Postgres-only

Usa schemas, así que requiere PostgreSQL (no SQLite/MySQL).

!
En 2019 se usaba django-tenant-schemas, pero está sin mantenimiento. Hoy instala django-tenants.
⏱ 120 s · Corrección clave respecto a la charla original. Mismo autor original, fork activo. pip install django-tenants.

Puesta en marcha

Instalación

Django 5, PostgreSQL y el driver psycopg 3.

bash
$ pip install django django-tenants "psycopg[binary]" $ django-admin startproject aulasass . $ python manage.py startapp customers

Base de datos

Cambia el ENGINE por el backend de django-tenants.

        "PASSWORD": "...",
        "HOST": "localhost",
        "PORT": "5432",
    }
}
✓
Este backend es el que dirige las consultas al schema activo según el search_path.
⏱ 90 s · El único cambio "mágico" en la conexión. Todo lo demás es configuración normal de Django.

Configuración · 3

Shared, tenant e instaladas

settings.py
SHARED_APPS = [
    "django_tenants",        # obligatorio
    "customers",             # client + domain
    "django.contrib.contenttypes",
    "django.contrib.auth",
    "django.contrib.sessions",
    "django.contrib.admin",
]

TENANT_APPS = [
    "django.contrib.contenttypes",
    "cursos", "alumnos",   # datos por tenant
]

INSTALLED_APPS = list(SHARED_APPS) + [
    a for a in TENANT_APPS if a not in SHARED_APPS
]
i
SHARED_APPS van al schema public; TENANT_APPS se crean en cada schema de tenant.
⏱ 150 s · La distinción más importante del setup. contenttypes aparece en ambos porque cada schema necesita las tablas base de Django.

Modelo de tenant y enrutador

settings.py

i
Le dicen a Django qué modelos representan al tenant y sus dominios, y qué apps sincronizar en cada schema.
⏱ 90 s · El router decide qué apps van a public y cuáles a cada tenant al migrar. Es lo que hace que migrate_schemas sepa dónde ir.
Los modelos

Client y Domain

customers/models.py
from django_tenants.models import TenantMixin, DomainMixin
from django.db import models

class Client(TenantMixin):
    nombre = models.CharField(max_length=100)
    plan = models.CharField(max_length=20, default="basico")
    auto_create_schema = True

class Domain(DomainMixin):
    pass
✓
TenantMixin aporta schema_name; DomainMixin aporta domain e is_primary. Añade tus propios campos.
⏱ 120 s · Client guarda el schema; Domain guarda el subdominio. Con auto_create_schema=True, al guardar se crea y migra el schema.
El dominio principal

El tenant público

Tu dominio principal también es un tenant, respaldado por el schema public.

shell
from customers.models import Client, Domain

public = Client(schema_name="public", nombre="AulaSaaS")
public.save()
Domain.objects.create(
    domain="tuapp.com", tenant=public, is_primary=True,
)
!
Sin este tenant, tuapp.com responde 404: el middleware no encuentra a quién servir.
⏱ 90 s · Detalle que sorprende a todos: la web principal es un tenant más, con schema_name="public".
Migraciones

Migrar schemas

bash
$ python manage.py migrate_schemas --shared $ python manage.py migrate_schemas --tenant $ python manage.py migrate_schemas # ambos
--shared solo el schema public
--tenant todos los schemas de tenants
i
No uses migrate a secas: migrate_schemas aplica cada app en el schema que le toca.
⏱ 120 s · Shared primero, luego tenants. En despliegues, esto es parte del pipeline de release.
A escala

Migraciones en paralelo

Con cientos de tenants, migrar uno a uno tarda demasiado.

bash
$ python manage.py migrate_schemas \ --executor=multiprocessing --parallel=8
!
Las migraciones deben ser idempotentes y rápidas: un error en un schema puede dejar tenants desincronizados.
⏱ 90 s · El ejecutor multiprocessing reparte los schemas entre procesos. En mantenimientos, migra por lotes.

comando

✓

En producción

Provisioning al registrarse

Crear un schema y migrarlo tarda; no lo hagas en la petición de registro.

tareas.py
from celery import shared_task
from customers.models import Client

@shared_task
def provisionar(tenant_id):
    tenant = Client.objects.get(id=tenant_id)
    tenant.create_schema(check_if_exists=True)
    # sembrar datos iniciales, admin, plan...
!
Marca el tenant como pendiente hasta que el schema esté listo: el middleware debe ignorar tenants sin terminar.
⏱ 120 s · Provisioning asíncrono con Celery. Evita bloquear al usuario y permite reintentos si algo falla a mitad.
En la vista

Acceder al tenant actual

vistas.py
from django.db import connection

def inicio(request):
    tenant = request.tenant            # objeto Client
    schema = connection.schema_name    # "acme" o "public"
    nombre = request.tenant.nombre
    return render(request, "inicio.html", {"colegio": nombre})
✓
request.tenant es útil para branding y features; connection.schema_name para lógica de datos.
⏱ 90 s · El middleware pone el tenant en la request. Vistas y templates personalizan sin saber de dominios.
Qué va dónde

Datos compartidos vs por tenant

public · shared
Compartido

Tenants, dominios, usuarios globales, planes, facturación, catálogos.

schema del tenant
Aislado

Cursos, alumnos, notas, asistencia, configuración y branding del colegio.

i
Regla: si dos clientes podrían discrepar sobre un dato, va por tenant. Si es común a todos, va en public.
⏱ 90 s · Esta decisión se toma una vez y cuesta cambiarla. Pensarla bien antes de escribir modelos.

Probar

Tests en multitenant

django-tenants aporta clases de test que crean un tenant temporal.

cursos/tests.py
from django_tenants.test.cases import TenantTestCase

class CursoTest(TenantTestCase):
    def test_crear_curso(self):
        Curso.objects.create(nombre="Matemática")
        self.assertEqual(Curso.objects.count(), 1)
!
Los tests con schemas usan TransactionTestCase: son más lentos y no se paralelizan igual que los normales.
⏱ 120 s · TenantTestCase crea y migra un schema para cada test. Ojo: con muchos tests, el tiempo de migración se nota.

Archivos

Media y archivos por tenant

Las subidas deben aislarse igual que los datos: una ruta por tenant.

storage.py
from django.db import connection

def ruta_por_tenant(instance, filename):
    schema = connection.schema_name
    return f"{schema}/documentos/{filename}"

class Documento(models.Model):
    archivo = models.FileField(upload_to=ruta_por_tenant)
!
Con S3, sirve los archivos con URLs firmadas y prefijo por tenant; nunca uses un bucket plano y público.
⏱ 120 s · El aislamiento no es solo de base de datos. Un bucket compartido mal servido puede filtrar documentos entre colegios.
Tareas en background

Celery por tenant

Un worker no tiene subdominio: hay que decirle explícitamente en qué schema trabajar.

tareas.py
from django_tenants.utils import schema_context

@shared_task
def enviar_reporte(schema_name, curso_id):
    with schema_context(schema_name):
        # aquí el ORM usa el schema del tenant
        generar_pdf(curso_id)
✓
Siempre pasa el schema_name a la tarea y envuélvela en schema_context: sin eso, usa public.
⏱ 120 s · Error clásico: la tarea corre sin tenant y consulta public. schema_context y tenant_context son las herramientas clave.

Multitenancy fuera de Django y lecciones reales

⏱ 10 s · Divisor. El patrón es agnóstico del framework; veamos cómo se ve con SQLAlchemy.
Más allá de Django

Multitenancy con SQLAlchemy

enfoque A
schema por sesión

Igual que django-tenants: search_path por petición. Reutiliza el mismo esquema SQL.

enfoque B
tenant_id + RLS

Cada tabla lleva tenant_id; Postgres lo refuerza con RLS.

i
La decisión no cambia: compartir por filas o separar por schema. El framework solo cambia dónde fijas el contexto.
⏱ 90 s · Los mismos 3 patrones aplican en FastAPI. Aquí mostramos los dos más usados con SQLAlchemy.
Enfoque A

schema-per-tenant con SQLAlchemy

db.py
from sqlalchemy import event
from contextvars import ContextVar

tenant_ctx = ContextVar("schema", default="public")

@event.listens_for(engine, "checkout")
def set_schema(dbapi_conn, record):
    schema = tenant_ctx.get()
    dbapi_conn.cursor().execute(
        f'SET search_path TO "{schema}", public'
    )
!
Valida siempre el schema contra una lista blanca antes de interpolarlo: aquí también hay riesgo de inyección.
⏱ 120 s · El evento checkout fija el search_path por conexión según un ContextVar que pones en el middleware. Muy parecido a django-tenants por dentro.
Enfoque B

tenant_id + RLS con SQLAlchemy

modelos.py
class Curso(Base):
    __tablename__ = "cursos"

    id: Mapped[int] = mapped_column(primary_key=True)
    tenant_id: Mapped[int] = mapped_column(index=True)
    nombre: Mapped[str]

# RLS en Postgres usa current_setting('app.tenant_id')
✓
En cada petición: SET app.tenant_id = ... y Postgres filtra aunque olvides el WHERE.
⏱ 120 s · Combina filtrado en el ORM (rendimiento, índices) con RLS (seguridad). Defensa en profundidad.
